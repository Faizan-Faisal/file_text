## §1. Executive Summary and v7 → v8 Change Summary

Phase 5 adds CSV-based bulk student registration for Main Admin, processing up to 100 rows synchronously via the existing `register_student()` method.

### v7 → v8 changes

| # | Issue | v7 behavior | v8 fix |
|---|---|---|---|
| 1 | After-loop reads/inserts child rows without ownership against concurrent reconciliation | After-loop runs unprotected; reconciliation could race it | After-loop acquires an exclusive lock on the session row via a conditional UPDATE (`SET heartbeat WHERE status='PROCESSING'`) with a 5-second `lock_timeout`. All child mutations, counter recalculation, and audit are within this single locked transaction. |
| 2 | Reconciliation decision table incomplete for contradictory evidence | Only normal consistent cases defined | Complete table: SUCCEEDED+no audit, FAILED+audit, NOT_PROCESSED+audit, duplicate audits, entity-ID mismatch, malformed metadata → all classified CONTRADICTION. Any contradiction → reconciliation ROLLS BACK; session reverts to PROCESSING; error returned to admin. |
| 3 | RECONCILING state claimed as externally observable but never durably committed under single-transaction model | State-transition table, API, and stale RECONCILING reclaim all presume RECONCILING is durable | RECONCILING acknowledged as transient in-transaction state: never visible to concurrent reads under READ COMMITTED. Stale RECONCILING reclaim rule removed. API GET never returns RECONCILING. Claim SQL checks only `status='PROCESSING' AND heartbeat stale`. |
| 4 | Generic except covers registration, T3, AND email scheduling | Email failure after SUCCEEDED T3 sets OUTCOME_UNCERTAIN | Three separate try blocks: T2 (registration), T3 (outcome persistence), email. Email failure after committed SUCCEEDED is logged as a warning; import continues to next row. |
| 5 | NOT_PROCESSED + `was_attempted` semantics unclear | `was_attempted=NULL` for all reconciled STARTED rows | Three-way semantic preserved. NOT_PROCESSED clarified as "no committed registration found" (not "never attempted"). OUTCOME_UNCERTAIN resolved to NOT_PROCESSED keeps `was_attempted=TRUE` (invocation known). |
| 6 | 90-day/30-day retention claimed but no purge mechanism exists | Retention proposed as though implemented | Retention distinguished as PROPOSED (pending future purge). Current implementation: indefinite retention, explicitly accepted as temporary. Full purge specification documented (child first, FK prevents parent deletion while children exist, audit retained). |

### Additional refinements

| # | Refinement | Change |
|---|---|---|
| A1 | Audit key `bulk_upload_row_number` stores `valid_row_index`, not CSV record number | Renamed to `bulk_upload_valid_row_index` |
| A2 | Targeted audit index for reconciliation | Proposed as pending decision: partial index on `(event_metadata->>'bulk_upload_session_id')` where `action='student.registered'` |

### §3D. State-Transition Table

**Externally observable states:** PENDING_CONFIRMATION, EXPIRED, PROCESSING, COMPLETED, PARTIALLY_COMPLETED, FAILED.

**Transient in-transaction state:** RECONCILING — set within the reconciliation transaction but never committed as RECONCILING. The transaction either commits with a terminal status or rolls back to PROCESSING. Under READ COMMITTED isolation, concurrent reads never observe RECONCILING. Retained in the CHECK constraint for in-transaction use only.

| Current state | Trigger | New state | Condition |
|---|---|---|---|
| PENDING_CONFIRMATION | Confirm endpoint | PROCESSING | `expires_at > now()` |
| PENDING_CONFIRMATION | Any read (lazy) | EXPIRED | `expires_at ≤ now()` |
| PROCESSING | Import completes, all rows definitive | COMPLETED | `imported = valid_count`, no STARTED/uncertain |
| PROCESSING | Import completes, all rows definitive | PARTIALLY_COMPLETED | `0 < imported < valid_count`, no STARTED/uncertain |
| PROCESSING | Import completes, all rows definitive | FAILED | `imported = 0`, no STARTED/uncertain |
| PROCESSING | Import interrupted, unresolved rows | PROCESSING (stays) | No terminal write; heartbeat goes stale |
| PROCESSING | Reconciliation (single tx) | COMPLETED / PARTIALLY_COMPLETED / FAILED | Heartbeat stale, all rows resolved, no contradictions |
| PROCESSING | Reconciliation (single tx), contradictions | PROCESSING (stays) | Reconciliation rolls back |

**Disallowed:** EXPIRED, COMPLETED, PARTIALLY_COMPLETED, FAILED → anything. PROCESSING → EXPIRED.

**Why stale RECONCILING reclaim is removed:** Under the single-transaction model, RECONCILING is never committed. If the reconciliation transaction rolls back (connection loss, contradiction, any error), the session reverts to PROCESSING. The session's heartbeat is stale (last updated by the import loop or after-loop). A subsequent reconciliation claim succeeds via the `status='PROCESSING' AND heartbeat stale` check. No separate RECONCILING reclaim path is needed.

        )

    CONSTRAINT ck_bulk_sessions_preview_counts CHECK (
        valid_count >= 0 AND invalid_count >= 0
        AND total_rows = valid_count + invalid_count
    ),
    CONSTRAINT ck_bulk_sessions_import_counts CHECK (
        imported_count >= 0 AND failed_count >= 0
        AND not_processed_count >= 0 AND uncertain_count >= 0
        AND (CASE

## §5. CSV Parsing and Preview

### §5.1. File acceptance (content-based)

Read up to 5,000,001 bytes. If more data remains → 413.

1. UTF-8 decode. Strip BOM. Failure → 422.
2. Strict CSV parse: `csv.reader(strict=True)`. Save/restore `csv.field_size_limit(8192)` around parsing to avoid process-wide side effects. Parse failure → 422.
3. Header validation (§5.2).
4. Column-count consistency: every non-blank data record must have exactly the same field count as the header. Mismatch → 400 citing record number.
5. Count non-blank data records. Zero → 400. >100 → 400.

### §5.2. Headers

Required (case-insensitive, trimmed): `first_name`, `last_name`, `email`, `roll_number`, `program_code`, `semester_level`, `admission_term`. Optional: `section_name`, `phone`, `address`. Missing required → 400. Duplicate → 400. Unknown → 400.

### §5.3. Record numbering

`csv_record_number`: 1-indexed ordinal of non-blank data records after the header. A multi-line quoted record counts as one record. Blank records (all fields empty after strip) are skipped.

`valid_row_index`: assigned sequentially from 1 through `valid_count` to records that pass all preview validations, in `csv_record_number` order.

### §5.4. Formula-cell validation

Checked columns: all except `phone`. Phone exempt — `normalize_phone()` rejects non-phone values.

Rules: First char in `{= @ \t \r \n}` → reject. First char is `+` or `-` → reject. First non-whitespace in `{= + - @}` → reject.

### §5.5. Semester-level validation

Parse as integer, check `≥ 1`. After resolving program, check `≤ program.duration_semesters`. No arbitrary cap in CSV code.

### §5.6. `preview_invalid_results`

PII-free error summaries for invalid records. Immutable after upload (not in UPDATE grants). Never scrubbed.

### §5.7. `expires_at`

`created_at + INTERVAL '30 minutes'`. Immutable after upload.

## §7. T1 / T2 / T3 Transaction Boundaries

### §7.1. T1 — STARTED child row (ON CONFLICT safe)

```
T1 for valid_row_index = I, csv_record_number = R:

  INSERT INTO bulk_upload_row_results
    (upload_session_id, valid_row_index, csv_record_number, status, was_attempted)
    VALUES (:session_id, I, R, 'STARTED', NULL)
    ON CONFLICT (upload_session_id, valid_row_index) DO NOTHING
    RETURNING id

  IF RETURNING yields a row (new insert):
    UPDATE bulk_upload_sessions
      SET last_started_valid_index = I,
          processing_heartbeat_at = now(),
          updated_at = now()
      WHERE id = :session_id AND status = 'PROCESSING'
    IF rowcount = 0 → ROLLBACK → FENCED
    ELSE → COMMIT → PROCEED

  IF RETURNING yields no rows (conflict):
    ROLLBACK → SKIP
```

**ON CONFLICT DO NOTHING proof:**
1. `DO NOTHING` modifies zero columns. Existing status/student_id/errors untouched.
2. On conflict, the loop skips the row. T2 never called. No duplicate registration.
3. Heartbeat/progress NOT updated for skipped rows.

**Behavior by existing child-row status:**

| Existing | T1 result | T2? | Rationale |
|---|---|---|---|
| STARTED | SKIP | No | May have been attempted. Reconciliation resolves. |
| SUCCEEDED | SKIP | No | Already done. |
| FAILED | SKIP | No | Already done. |
| NOT_PROCESSED | SKIP | No | Already classified. |
| OUTCOME_UNCERTAIN | SKIP | No | Reconciliation resolves. |

### §7.2. T2 — Registration

`register_student()` owns its own transaction. Commits at [service.py:309](backend/app/modules/students/service.py#L309) or rolls back at [248/311/322](backend/app/modules/students/service.py#L248). The import loop does not control this boundary.

### §7.3. T3 — Outcome persistence (child + parent atomic)

```
T3 for valid_row_index = I, intended outcome = O:

  BEGIN

  UPDATE bulk_upload_row_results
    SET status = O, student_id = :sid, was_attempted = TRUE,
        first_name = :fn, last_name = :ln, roll_number = :rn,
        error_code = :ec, error_message = :em,
        corrective_action = :ca, is_retryable = :ir,
        updated_at = now()
    WHERE upload_session_id = :session_id
      AND valid_row_index = I
      AND status = 'STARTED'

  IF child_rowcount = 1:
    UPDATE bulk_upload_sessions
      SET <counter>_count = <counter>_count + 1,
          processing_heartbeat_at = now(),
          updated_at = now()
      WHERE id = :session_id AND status = 'PROCESSING'
    IF parent_rowcount = 0 → ROLLBACK → FENCED
      (child update also rolled back — same transaction)
    ELSE → COMMIT → OK

  IF child_rowcount = 0:
    existing = SELECT status FROM bulk_upload_row_results
      WHERE upload_session_id = :session_id AND valid_row_index = I
    IF existing IS NULL:
      ROLLBACK → INCONSISTENT (child row missing — should not happen)
    ELSE IF existing = O:
      ROLLBACK → ALREADY_WRITTEN (idempotent; counter was already incremented)
    ELSE:
      ROLLBACK → INCONSISTENT (status mismatch)
```

**Key properties:**
- Child UPDATE + parent counter UPDATE in same transaction. Parent failure → both rolled back.
- Zero-row child UPDATE → read existing status → verify consistency. Never silently ignored.

## §8. Registration Fencing and Lock Ordering

### §8.1. Lock ordering

```
bulk_upload_sessions (FOR SHARE)  ← only when bulk_origin provided
  → term (FOR SHARE)
    → department/program/section (FOR SHARE)
      → student/placement (FOR UPDATE, correction only)
```

### §8.2. FOR SHARE inside register_student()

```python
@dataclass(frozen=True)
class BulkImportOrigin:
    upload_session_id: uuid.UUID
    row_index: int  # valid_row_index
```

Before `_lock_and_validate()`:

```python
if bulk_origin is not None:
    session_status = self.db.scalar(
        select(BulkUploadSession.status)
        .where(BulkUploadSession.id == bulk_origin.upload_session_id)
        .with_for_update(read=True)
    )
    if session_status != BulkUploadStatus.PROCESSING.value:
        raise BulkImportSessionFencedError(...)
```

**Interaction with reconciliation's exclusive lock:**
- If reconciliation holds the exclusive lock → FOR SHARE blocks until reconciliation commits (terminal) or rolls back (PROCESSING).
- After commit: FOR SHARE reads terminal → `BulkImportSessionFencedError` → no student.
- After rollback: FOR SHARE reads PROCESSING → registration proceeds → audit visible for future reconciliation.

**Interaction with after-loop's exclusive lock:** Same mechanism. After-loop holds exclusive lock → FOR SHARE blocks → after commit, reads current status → proceeds or raises fencing error accordingly.

## §9. Import-Loop State Machine, After-Loop Ownership, and Exception Boundaries

### §9.1. ImporterState enum

```python
class ImporterState(StrEnum):
    NORMAL = "NORMAL"
    FENCED = "FENCED"
    INTERRUPTED = "INTERRUPTED"
```

### §9.2. Import loop with separated exception boundaries (correction 4)

```python
importer_state = ImporterState.NORMAL

for vr in valid_rows:
    index = vr["valid_row_index"]
    csv_rec = vr["csv_record_number"]

    # ── T1 ──
    t1 = persist_started(db, session_id, index, csv_rec)
    if t1 == T1Result.FENCED:
        importer_state = ImporterState.FENCED; break
    if t1 == T1Result.SKIP:
        continue

    # ── T2: Registration (separate try) ──
    reg_result = None
    reg_error = None
    try:
        reg_result = student_service.register_student(
            actor=actor, department_id=department_id,
            data=make_registration_data(vr),
            ip_address=ip_address,
            bulk_origin=BulkImportOrigin(session_id, index),
        )
    except BulkImportSessionFencedError:
        importer_state = ImporterState.FENCED; break
    except (StudentConflictError, StudentValidationError,
            StudentReferenceNotFoundError) as exc:
        reg_error = exc
    except Exception:
        # Unexpected T2 failure. Student may or may not exist.
        try:
            persist_outcome(db, session_id, index,
                outcome=RowOutcome.OUTCOME_UNCERTAIN,
                first_name=vr.get("first_name"), ...)
        except Exception:
            pass  # child stays STARTED
        importer_state = ImporterState.INTERRUPTED; break

    # ── T3: outcome persistence (separate try) ──
    if reg_result is not None:
        # T2 succeeded — persist SUCCEEDED
        try:
            t3 = persist_outcome(db, session_id, index,
                outcome=RowOutcome.SUCCEEDED,
                student_id=reg_result.student.id,
                first_name=reg_result.user.first_name,
                last_name=reg_result.user.last_name,
                roll_number=reg_result.student.roll_number)
        except Exception:
            # T3 failed. Student IS registered (T2 committed).
            # Child stays STARTED. Reconciliation: audit → SUCCEEDED.
            importer_state = ImporterState.INTERRUPTED; break

        if t3 == T3Result.FENCED:
            # Parent UPDATE returned 0. ROLLBACK undid child update.
            # Student IS registered. Reconciliation finds audit.
            importer_state = ImporterState.FENCED; break
        if t3 == T3Result.INCONSISTENT:
            importer_state = ImporterState.INTERRUPTED; break

        # ── Email (separate try — failure is non-fatal) ──
        try:
            schedule_email(background_tasks, email_sender,
                build_student_onboarding_email(
                    to=reg_result.user.email,
                    first_name=reg_result.user.first_name,
                    program_name=reg_result.program.name,
                    department_name=reg_result.department.name))
        except Exception:
            logger.warning("Email scheduling failed for row %d", index)
        # Continue to next row regardless of email outcome.

    elif reg_error is not None:
        # T2 raised business error — persist FAILED
        try:
            t3 = persist_outcome(db, session_id, index,
                outcome=RowOutcome.FAILED,
                error_code=classify_error(reg_error),
                error_message=str(reg_error),
                corrective_action=suggest_correction(reg_error),
                is_retryable=is_retryable(reg_error),
                first_name=vr.get("first_name"),
                last_name=vr.get("last_name"),
                roll_number=vr.get("roll_number"))
        except Exception:
            # T3 failed. T2 rolled back (no student).
            # Child stays STARTED. Reconciliation: no audit → NOT_PROCESSED.
            importer_state = ImporterState.INTERRUPTED; break

        if t3 == T3Result.FENCED:
            importer_state = ImporterState.FENCED; break
        if t3 == T3Result.INCONSISTENT:
            importer_state = ImporterState.INTERRUPTED; break
```

**Exception boundary summary:**

| Failure | Outcome | Email? | Loop? |
|---------|---------|--------|-------|
| T2 business error | FAILED (T3) | No | Continues |
| T2 unexpected error | OUTCOME_UNCERTAIN or STARTED | No | Breaks (INTERRUPTED) |
| T2 fencing | Child stays STARTED | No | Breaks (FENCED) |
| T3 exception (after T2 success) | Child stays STARTED; student IS registered | No | Breaks (INTERRUPTED) |
| T3 FENCED (after T2 success) | Child stays STARTED; student IS registered | No | Breaks (FENCED) |
| T3 exception (after T2 error) | Child stays STARTED; no student | No | Breaks (INTERRUPTED) |
| Email failure (after T3 SUCCEEDED) | SUCCEEDED (unchanged) | Attempted, failed | Continues |

### §9.3. After-loop ownership model (correction 1)

The after-loop acquires an exclusive lock on the session row before any child mutations. This prevents concurrent reconciliation from modifying children at the same time.

**Complete after-loop algorithm:**

```python
if importer_state == ImporterState.FENCED:
    # Session is being claimed by reconciliation.
    # Do NOT classify remaining rows. Do NOT write audit. Leave everything.
    pass

elif importer_state in (ImporterState.NORMAL, ImporterState.INTERRUPTED):
    try:
        # ── Step 0: Acquire ownership ──
        db.execute(text("SET LOCAL lock_timeout = '5s'"))

        ownership_rowcount = db.execute(
            update(BulkUploadSession)
            .where(BulkUploadSession.id == session_id)
            .where(BulkUploadSession.status == 'PROCESSING')
            .values(processing_heartbeat_at=func.now(),
                    updated_at=func.now())
        ).rowcount

        if ownership_rowcount == 0:
            # Session no longer PROCESSING (reconciliation committed
            # terminal, or some other state change).
            db.rollback()
            return  # Leave everything to reconciliation.

        # Exclusive lock now held. No reconciliation can claim
        # until this transaction commits or rolls back.

        # ── Step 1: Find rows with NO child record ──
        existing_indexes = set(db.scalars(
            select(BulkUploadRowResult.valid_row_index)
            .where(BulkUploadRowResult.upload_session_id == session_id)
        ).all())
        all_indexes = set(range(1, valid_count + 1))
        never_started = all_indexes - existing_indexes

        # ── Step 2: Insert NOT_PROCESSED for never-started ──
        for mi in sorted(never_started):
            csv_rec = index_to_csv_record[mi]
            db.execute(
                pg_insert(BulkUploadRowResult).values(
                    upload_session_id=session_id,
                    valid_row_index=mi,
                    csv_record_number=csv_rec,
                    status='NOT_PROCESSED',
                    was_attempted=False)
            )

        # ── Step 3: Recalculate ALL counters from child table ──
        counts = dict(db.execute(
            select(BulkUploadRowResult.status, func.count())
            .where(BulkUploadRowResult.upload_session_id == session_id)
            .group_by(BulkUploadRowResult.status)
        ).all())

        succeeded = counts.get('SUCCEEDED', 0)
        failed = counts.get('FAILED', 0)
        not_processed = counts.get('NOT_PROCESSED', 0)
        uncertain = counts.get('OUTCOME_UNCERTAIN', 0)
        started = counts.get('STARTED', 0)
        unresolved = uncertain + started

        # ── Step 4: Terminal or interrupted ──
        if unresolved > 0:
            # 4a: Unresolved rows remain. No terminal write.
            parent_rowcount = db.execute(
                update(BulkUploadSession)
                .where(BulkUploadSession.id == session_id)
                .where(BulkUploadSession.status == 'PROCESSING')
                .values(
                    imported_count=succeeded,
                    failed_count=failed,
                    not_processed_count=not_processed,
                    uncertain_count=uncertain + started,
                    updated_at=func.now())
            ).rowcount
            if parent_rowcount == 0:
                db.rollback(); return

            audit_service.record(
                action=AuditAction.BULK_IMPORT_INTERRUPTED,
                entity_type=AuditEntityType.BULK_UPLOAD_SESSION,
                entity_id=session_id,
                actor_user_id=actor.id,
                metadata={"unresolved_count": unresolved,
                          "imported_count": succeeded,
                          "failed_count": failed},
                ip_address=ip_address)
            db.commit()

        else:
            # 4b: All rows definitive. Verify count.
            total = succeeded + failed + not_processed
            if total != valid_count:
                db.rollback(); return  # Inconsistent → reconciliation.

            terminal = determine_terminal_status(succeeded, valid_count)
            parent_rowcount = db.execute(
                update(BulkUploadSession)
                .where(BulkUploadSession.id == session_id)
                .where(BulkUploadSession.status == 'PROCESSING')
                .values(
                    status=terminal,
                    imported_count=succeeded,
                    failed_count=failed,
                    not_processed_count=not_processed,
                    uncertain_count=0,
                    validated_rows=text("'[]'::jsonb"),
                    completed_at=func.now(),
                    updated_at=func.now())
            ).rowcount
            if parent_rowcount == 0:
                db.rollback(); return

            audit_service.record(
                action=AuditAction.BULK_IMPORT_COMPLETED,
                entity_type=AuditEntityType.BULK_UPLOAD_SESSION,
                entity_id=session_id,
                actor_user_id=actor.id,
                metadata={"status": terminal,
                          "imported_count": succeeded,
                          "failed_count": failed,
                          "not_processed_count": not_processed},
                ip_address=ip_address)
            db.commit()

    except Exception:
        try: db.rollback()
        except Exception: pass
        # Session stays PROCESSING → reconciliation.
```

**Ownership-conflict proof (after-loop vs. reconciliation):**

| Scenario | After-loop | Reconciliation | Outcome |
|---|---|---|---|
| After-loop acquires lock first | Proceeds; commits | Blocks on row lock → after commit, sees terminal or fresh heartbeat → 0 rows or timeout → 409 or 503 | After-loop wins. |
| Reconciliation acquires lock first | Blocks on row lock → after reconciliation commits (terminal), `WHERE status='PROCESSING'` matches 0 → ownership_rowcount=0 → returns | Proceeds; commits terminal | Reconciliation wins. |
| Reconciliation acquires lock, then rolls back (contradiction) | Unblocked; sees PROCESSING with stale heartbeat → ownership_rowcount=1 → proceeds | Rolled back; no changes persisted | After-loop wins. |
| After-loop lock_timeout fires | Rolls back; session stays PROCESSING → reconciliation later | Proceeds eventually | Reconciliation wins. |

**At no point do both commit child mutations.** The exclusive row lock serializes them.

### §9.4. Broken session / connection loss

If the db connection is unavailable: all after-loop operations fail → `except Exception` → rollback (may also fail) → session stays PROCESSING with stale heartbeat → reconciliation.

If the SQLAlchemy session is in error state: same path. `get_db()`'s `finally: db.close()` cleans up.

## §10. Reconciliation: Single-Transaction Model with Contradiction Handling

### §10.1. Transaction structure

The entire reconciliation — claim, reads, classifications, child mutations, counter recalculation, terminal write, scrubbing, and audit — runs in a **single database transaction**. The claim UPDATE's implicit exclusive row lock is held until COMMIT/ROLLBACK.

### §10.2. Claim

```sql
BEGIN;
SET LOCAL lock_timeout = '10s';

UPDATE bulk_upload_sessions
SET status = 'RECONCILING',
    reconciliation_claimed_by = :actor_id,
    reconciliation_started_at = now(),
    reconciliation_claim_token = :new_token,
    updated_at = now()
WHERE id = :upload_id
  AND status = 'PROCESSING'
  AND processing_heartbeat_at < now() - INTERVAL '5 minutes'
RETURNING id, reconciliation_claim_token, valid_count;
```

Lock timeout → ROLLBACK → 503. Zero rows → ROLLBACK → 409.

**No stale RECONCILING reclaim.** The WHERE clause checks only `status='PROCESSING'`. Under the single-transaction model, RECONCILING is never committed. If a reconciliation transaction rolls back, the session reverts to PROCESSING with stale heartbeat, and this same check succeeds on the next attempt.

### §10.3. Read phase (same transaction)

**Step 1 — Child rows:**
```sql
SELECT valid_row_index, status, student_id
FROM bulk_upload_row_results
WHERE upload_session_id = :upload_id;
```

**Step 2 — `validated_rows`** for `valid_row_index → csv_record_number` mapping.

**Step 3 — Audit records:**
```sql
SELECT entity_id,
       event_metadata->>'bulk_upload_valid_row_index' AS raw_index,
       event_metadata->>'bulk_upload_session_id' AS raw_session_id
FROM audit_logs
WHERE action = 'student.registered'
  AND event_metadata->>'bulk_upload_session_id' = :upload_id_text;
```

For each returned row, validate:
- `raw_index` is not NULL and parses as a positive integer.
- `raw_session_id` matches `:upload_id_text`.
- `entity_id` is not NULL.
- No duplicate `row_index` values.

If any validation fails → contradiction (§10.4).

Build maps: `audit_by_index: {row_index → entity_id}`, `child_by_index: {row_index → (status, student_id)}`.

### §10.4. Complete reconciliation decision table (correction 2)

**Normal cases (consistent evidence):**

| Child status | Audit? | Action | `was_attempted` |
|---|---|---|---|
| None | No | INSERT NOT_PROCESSED | FALSE |
| None | Yes | INSERT SUCCEEDED (student_id from audit) | TRUE |
| STARTED | No | UPDATE → NOT_PROCESSED | NULL |
| STARTED | Yes | UPDATE → SUCCEEDED (student_id from audit) | TRUE |
| OUTCOME_UNCERTAIN | No | UPDATE → NOT_PROCESSED | TRUE (keep) |
| OUTCOME_UNCERTAIN | Yes | UPDATE → SUCCEEDED (student_id from audit) | TRUE (keep) |
| SUCCEEDED | Yes, entity_id matches child student_id | Keep | TRUE (keep) |
| FAILED | No | Keep | TRUE (keep) |
| NOT_PROCESSED | No | Keep | Keep existing |

**Contradictory cases (fail closed — reconciliation ROLLS BACK):**

| Case | Child status | Audit status | Classification |
|---|---|---|---|
| C1 | SUCCEEDED | No audit for this index | CONTRADICTION |
| C2 | FAILED | Audit exists for this index | CONTRADICTION |
| C3 | NOT_PROCESSED | Audit exists for this index | CONTRADICTION |
| C4 | SUCCEEDED | Audit exists but `entity_id ≠ child.student_id` | CONTRADICTION |
| C5 | Any | Multiple audit records for same index | CONTRADICTION |
| C6 | Any | Audit `raw_index` not parseable as integer | CONTRADICTION |
| C7 | Any | Audit `raw_index` is NULL | CONTRADICTION |

**On any contradiction:**

1. The reconciliation transaction ROLLS BACK. The claim (RECONCILING) and all child-row mutations are undone. The session reverts to PROCESSING.
2. The endpoint returns 409 with a detailed error response listing each contradiction: `{"contradictions": [{"valid_row_index": 5, "type": "SUCCEEDED_NO_AUDIT", "details": "..."}]}`.
3. The admin investigates the audit_logs and child table directly (requires database access).
4. After manual correction, the admin retries reconciliation.

**Rationale:** Contradictions indicate data integrity issues (bugs or manual intervention). Terminalizing with contradictory evidence would permanently record incorrect results. Rolling back is safe — the session reverts to its prior state, and no incorrect data is committed.

### §10.5. Write phase (same transaction, only if no contradictions)

**Step 5 — Apply changes:** Update child rows where classification changed. Insert child rows for missing indexes.

**Step 6 — Recalculate counters** from child table (same query as after-loop step 3).

**Step 7 — Verify:** `total = succeeded + failed + not_processed`. Verify `total == valid_count` and no STARTED/UNCERTAIN remain. If not → ROLLBACK (should not happen if decision table is correct).

**Step 8 — Terminal write (defense-in-depth token):**

```sql
UPDATE bulk_upload_sessions
SET status = :terminal,
    imported_count = :c1, failed_count = :c2,
    not_processed_count = :c3, uncertain_count = 0,
    validated_rows = '[]',
    completed_at = now(),
    was_reconciled = TRUE,
    updated_at = now()
WHERE id = :upload_id
  AND status = 'RECONCILING'
  AND reconciliation_claim_token = :my_token
RETURNING id;
```

0 rows → ROLLBACK (should not happen — this transaction set RECONCILING and holds the lock).

**Step 9 — Audit:** `bulk_import.reconciled` via `AuditService.record()` (flush).

**Step 10 — COMMIT.** All child mutations, counters, terminal status, scrubbing, and audit committed atomically.

### §10.6. Interaction with concurrent after-loop

The after-loop also acquires an exclusive lock on the session row (§9.3 step 0). The row lock serializes the two operations:

| After-loop first | Reconciliation blocks → after-loop commits → reconciliation sees terminal or fresh heartbeat → 0 rows |
|---|---|
| Reconciliation first | After-loop blocks → reconciliation commits terminal → after-loop sees `status ≠ 'PROCESSING'` → returns |
| Reconciliation first, then rolls back (contradiction) | After-loop unblocked → sees PROCESSING → proceeds |

Both cannot commit child mutations for the same session. ✓

## §11. Outcome Semantics and Count Invariants

### §11.1. Outcome definitions (correction 5)

| Outcome | Meaning | `was_attempted` | Student created? |
|---|---|---|---|
| SUCCEEDED | Audit record confirms student created and committed. | TRUE | Yes |
| FAILED | Registration invoked, known business error, rolled back. Error details durably recorded. | TRUE | No |
| NOT_PROCESSED | **No committed registration was found for this row.** This does NOT necessarily mean registration was never attempted — it means no durable evidence of a committed student exists. | FALSE, TRUE, or NULL (see §11.2) | No |
| OUTCOME_UNCERTAIN | Registration invoked, unexpected error. Not yet resolved. | TRUE | Unknown |
| SKIPPED_PREVIEW_INVALID | Failed preview validation. Never attempted. | — (not in child table) | No |

### §11.2. `was_attempted` × status combinations

| Status | `was_attempted` | Scenario |
|---|---|---|
| SUCCEEDED | TRUE | T2 committed; audit proves it |
| FAILED | TRUE | T2 invoked; business error |
| NOT_PROCESSED | FALSE | Never started (after-loop: no child row); reconciliation: no child + no audit |
| NOT_PROCESSED | TRUE | Was OUTCOME_UNCERTAIN (import loop knew T2 was invoked); reconciliation resolved: no audit → NOT_PROCESSED. Invocation known, but no committed student. |
| NOT_PROCESSED | NULL | Was STARTED; reconciliation resolved: no audit. Whether T2 was invoked is indeterminate. |
| OUTCOME_UNCERTAIN | TRUE | Pending resolution by reconciliation |

**API display per `was_attempted`:**
- `true`: "Registration was invoked for this record."
- `false`: "Registration was not invoked for this record."
- `null` (displayed as `null` in JSON, empty in CSV): "Whether registration was invoked cannot be determined."

### §11.3. Database-enforced invariants

Same as v7: `ck_bulk_sessions_preview_counts`, `ck_bulk_sessions_import_counts` (terminal: `sum = valid_count AND uncertain = 0`; non-terminal: `sum ≤ valid_count`), `uq_row_results_session_index`.

### §11.4. Application-enforced invariants

After-loop (§9.3 step 4b): verify `succeeded + failed + not_processed == valid_count` before terminal write.

Reconciliation (§10.5 step 7): verify `total == valid_count` and no unresolved rows.

## §12. API Contracts

### §12.1. Upload — `POST /admin/bulk-uploads`

Permission: `student.bulk_import`. Request: `multipart/form-data` — `file` (≤5 MB), `department_id`. Response 201: upload_id, status, counts, preview (valid + invalid rows), expires_at. Errors: 400, 409 (zero valid), 413, 422.

### §12.2. Confirm — `POST /admin/bulk-uploads/{id}/confirm`

Response 200. If all rows resolved: terminal status + results. If unresolved: `status: "PROCESSING"`, `needs_reconciliation: true`. Errors: 404, 409.

### §12.3. Get Status — `GET /admin/bulk-uploads/{id}`

**Observable states in response:** PENDING_CONFIRMATION, EXPIRED, PROCESSING, COMPLETED, PARTIALLY_COMPLETED, FAILED. **Never RECONCILING** — if reconciliation is in progress, the concurrent read sees the last committed state: PROCESSING. The response includes `is_stale` and `needs_reconciliation` for PROCESSING sessions.

PENDING_CONFIRMATION: full preview. EXPIRED: stub. PROCESSING: live counters, `is_stale`, `needs_reconciliation`. Terminal: child-table results (first_name, last_name, roll_number, `was_attempted`, status, student_id, error info) + `preview_invalid_results`. No email/phone/address.

### §12.4. Reconcile — `POST /admin/bulk-uploads/{id}/reconcile`

Response 200: terminal results. Response 409 with `contradictions` array: reconciliation detected data integrity issues, rolled back (§10.4). Session stays PROCESSING. Response 409 (not eligible): session not stale PROCESSING. Response 503: lock timeout.

### §12.5. Report — `GET /admin/bulk-uploads/{id}/report`

`text/csv; charset=utf-8`. Columns: `csv_record_number`, `valid_row_index`, `first_name`, `last_name`, `roll_number`, `status`, `was_attempted`, `error_code`, `error_message`, `corrective_action`, `is_retryable`. Includes child-table rows + preview-invalid rows (SKIPPED_PREVIEW_INVALID). Formula injection: prefix cells starting with `{= + - @ \t \r \n}`. Terminal only; 409 otherwise.

### §12.6. List — `GET /admin/bulk-uploads`

Paginated. Filters: `department_id`, `status`. Summary counters only.

## §13. Privacy, Retention, and Purge Policy (correction 6)

### §13.1. Data classification

| Location | PII | Scrubbing |
|---|---|---|
| `validated_rows` (parent) | YES: all parsed fields | Scrubbed to `[]` atomically with terminal write |
| `preview_invalid_results` (parent) | NONE: record numbers + error codes | Never scrubbed |
| Child: `first_name`, `last_name`, `roll_number` | YES: names + roll number | Retained until purge |
| Child: other columns | NONE | Retained until purge |
| Audit logs | Roll number, program, term (no email/phone/address) | Append-only; retained indefinitely |

### §13.2. Current implementation: indefinite retention

No purge mechanism exists in the current implementation. All bulk upload sessions, child rows, and audit records are retained indefinitely. **This is explicitly accepted as temporary** pending implementation of a purge mechanism in a future phase.

### §13.3. Proposed retention (pending approval — N11)

| State | Proposed retention | Measured from |
|---|---|---|
| Terminal (COMPLETED, PARTIALLY_COMPLETED, FAILED) | 90 days | `completed_at` |
| EXPIRED | 30 days | `expires_at` |

### §13.4. Future purge specification

When implemented, the purge operation must:

1. **Delete child rows first** (`bulk_upload_row_results`). The FK `ON DELETE RESTRICT` from child to parent prevents deleting the parent while children exist.
2. **Then delete parent** (`bulk_upload_sessions`).
3. **Audit records are NOT deleted.** The `audit_logs` table is append-only (trigger blocks UPDATE/DELETE; runtime role has SELECT+INSERT only). Audit records referencing purged sessions remain as historical evidence. The `entity_id` (session UUID) becomes a dangling reference, which is acceptable for audit history.
4. **PII in child rows** (`first_name`, `last_name`, `roll_number`) is removed by deleting the rows entirely. No selective scrubbing.
5. **Stale PROCESSING sessions** (import crashed, never reconciled, heartbeat far older than 90 days): included in the purge scope. These are effectively abandoned sessions with no terminal resolution.
6. **PENDING_CONFIRMATION sessions** past expiry + 30 days: `validated_rows` was already scrubbed to `[]` by lazy expiry. The session and any child rows (should be zero) are deleted.

The purge runs as a maintenance task (migration role, not application role), since the application role has no DELETE grants on these tables.

## §14. Audit Behavior

### §14.1. Actions and entity type

| Action | Value | Trigger |
|---|---|---|
| `BULK_IMPORT_UPLOADED` | `"bulk_import.uploaded"` | Session created |
| `BULK_IMPORT_CONFIRMED` | `"bulk_import.confirmed"` | Confirmation claim |
| `BULK_IMPORT_COMPLETED` | `"bulk_import.completed"` | Terminal write by after-loop |
| `BULK_IMPORT_INTERRUPTED` | `"bulk_import.interrupted"` | After-loop: unresolved rows remain; session stays PROCESSING |
| `BULK_IMPORT_RECONCILED` | `"bulk_import.reconciled"` | Reconciliation terminal write |

Entity type: `BULK_UPLOAD_SESSION` = `"bulk_upload_session"`.

`bulk_import.interrupted` and `bulk_import.completed` are mutually exclusive per session. A session that was interrupted and later reconciled has both `interrupted` and `reconciled` audit events.

### §14.2. Per-registration audit extension

When `bulk_origin` is provided:

```python
metadata["bulk_upload_session_id"] = str(bulk_origin.upload_session_id)
metadata["bulk_upload_valid_row_index"] = bulk_origin.row_index
```

**Renamed from v7's `bulk_upload_row_number`** (correction A1). The key name now accurately describes what it stores: the `valid_row_index`, not the CSV record number.

### §14.3. Reconciliation query

```sql
SELECT entity_id,
       event_metadata->>'bulk_upload_valid_row_index' AS raw_index
FROM audit_logs
WHERE action = 'student.registered'
  AND event_metadata->>'bulk_upload_session_id' = :upload_id_text;
```

Uses `ix_audit_logs_action` index on `action`.

### §14.4. Proposed: targeted partial index (pending approval — N7)

```sql
CREATE INDEX ix_audit_logs_bulk_session_id
ON audit_logs ((event_metadata->>'bulk_upload_session_id'))
WHERE action = 'student.registered'
  AND event_metadata ? 'bulk_upload_session_id';
```

This partial index covers only bulk-import-related student.registered records. Improves reconciliation query performance as the audit table grows. The existing `ix_audit_logs_action` index is sufficient for correctness but requires a post-filter on JSONB for each `student.registered` row.

## §15. Crash-Window Analysis

| # | Crash point | Child state | Audit? | Counter? | Recovery |
|---|---|---|---|---|---|
| CW1 | Upload INSERT before COMMIT | — | No | — | No session. Client retries. |
| CW2 | Upload committed | — | uploaded | — | Normal flow. |
| CW3 | Confirm committed, before loop | — | confirmed | — | PROCESSING, stale → reconcile: all NOT_PROCESSED. |
| CW4 | T1 committed, ACK lost | STARTED | No | heartbeat | INTERRUPTED → after-loop fails → reconcile: STARTED+no audit → NOT_PROCESSED. |
| CW5 | After T1, before T2 | STARTED | No | heartbeat | Same as CW4. |
| CW6 | During T2, before COMMIT | STARTED | No | from T1 | T2 rolls back. Same as CW5. |
| CW7 | T2 COMMIT sent, ACK lost | STARTED | Maybe | from T1 | Reconcile: if audit → SUCCEEDED; else → NOT_PROCESSED (was_attempted=NULL). |
| CW8 | After T2 success, before T3 | STARTED | Yes | from T1 | After-loop leaves STARTED → reconcile: audit → SUCCEEDED. |
| CW9 | After T2 rollback (error), before T3 | STARTED | No | from T1 | After-loop leaves STARTED → reconcile: no audit → NOT_PROCESSED (was_attempted=NULL). |
| CW10 | T3 committed, ACK lost | Final | Matches | Updated | INTERRUPTED → after-loop: T1 for next row sees existing → SKIP. |
| CW11 | After all rows, before after-loop | Per-row | Per-row | Per-row | After-loop runs. If fails → reconcile. |
| CW12 | After-loop ownership UPDATE committed, crash before rest | Heartbeat refreshed | No new | No new | Session PROCESSING, heartbeat fresh. Wait for stale → reconcile. |
| CW13 | After-loop committed | Children classified | Interrupted or completed | Recalculated | Terminal or PROCESSING with audit. |
| CW14 | Terminal COMMIT sent, ACK lost | All final | All present | All counted | If committed: terminal. If not: PROCESSING → reconcile. |

2. `confirm_and_process()`: confirmation claim, import loop with separated try blocks (§9.2), after-loop with ownership (§9.3).
3. `persist_started` (ON CONFLICT), `persist_outcome` (T3 with consistency check).
4. `POST /admin/bulk-uploads/{id}/confirm`. Lazy expiry.

1. `reconcile()`: single-transaction model (§10), contradiction detection, decision table, fail-closed rollback.
2. Remaining endpoints: reconcile, GET, report (CSV), list.
3. Per-state response shaping. RECONCILING never returned.
4. Tests: reconciliation, contradictions (CT1–CT9), RECONCILING visibility (RV1–RV4), ownership races (R1–R4), `was_attempted` per scenario.

### M4 — Integration and Edge Cases (2 days)

1. End-to-end: upload → confirm → results → report.
2. Concurrency: fencing, after-loop vs reconciliation.
3. Failure injection: DB disconnect, crash between T2 and T3, reconciliation after crash.
4. Count invariants. Child-table uniqueness. Idempotency.
5. Correction 1 scenario: T1→T2 commit→crash→STARTED remains→reconcile→SUCCEEDED.
