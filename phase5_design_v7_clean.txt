# Phase 5 — Bulk Student Registration: Technical Design v7

## §1. Executive Summary and v6 → v7 Change Summary

Phase 5 adds CSV-based bulk student registration for Main Admin, processing up to 100 rows synchronously via the existing `register_student()` method.

### v6 → v7 changes

| # | Issue (user correction) | v6 behavior | v7 fix |
|---|---|---|---|
| 1 | STARTED rows prematurely reclassified as NOT_PROCESSED | After-loop converts STARTED → NOT_PROCESSED for all unfinished rows | After-loop NEVER reclassifies STARTED rows. Only rows with no child record get NOT_PROCESSED. If any STARTED rows remain, session does not terminalize; stays PROCESSING for reconciliation. |
| 2 | Reconciliation ownership protects only final parent UPDATE; stale reconciler can mutate child rows | Claim is a separate committed transaction; child mutations unprotected | Entire reconciliation runs in a single transaction. The claim UPDATE's implicit row-level exclusive lock on `bulk_upload_sessions` is held until COMMIT/ROLLBACK. No other reconciler can re-claim or mutate children while the lock is held. |
| 3 | T1 plain INSERT can overwrite existing child outcomes on lost-ACK retry | Direct INSERT; retry causes IntegrityError or undefined behavior | T1 uses `INSERT ... ON CONFLICT (upload_session_id, valid_row_index) DO NOTHING RETURNING id`. Conflict → skip row entirely (no T2, no T3). Existing outcome is never overwritten. |
| 4 | Interrupted audit event contradicts "no terminal write on interruption" | §6.3 ties `bulk_import.interrupted` to terminal write; §14 says no terminal on interruption | `bulk_import.interrupted` is committed in its own after-loop transaction, separate from any terminal write. Session remains PROCESSING. At most one interrupted event per session in the synchronous model. |
| 5 | `was_attempted` claims knowledge the system cannot establish | `was_attempted BOOLEAN NOT NULL DEFAULT FALSE` — sets FALSE for reconciled STARTED rows even though attempt may have occurred | `was_attempted BOOLEAN` (nullable). NULL = cannot determine. THREE states: TRUE (definitely invoked), FALSE (definitely never invoked), NULL (indeterminate). |
| 6 | `csv_row_number` implies physical line number | Ambiguous terminology | Renamed to `csv_record_number`. Defined as 1-indexed ordinal of non-blank data records after the header. A multi-line quoted record counts as one record. |
| 7 | CSV parsing rules underspecified | No strict mode, no field-size limit, no column-count check | Strict parsing: `csv.reader(strict=True)`, `field_size_limit(8192)`, column-count consistency enforced, blank-row skipping defined, malformed records rejected. |
| 8 | T3 child and parent updates not explicitly in same transaction; zero-row child UPDATE silently ignored | Implicit but not stated | Explicitly: child outcome UPDATE and parent counter UPDATE are in the same transaction. Parent failure → both roll back. Zero-row child UPDATE → read existing status → verify consistency → log inconsistency if mismatch. |

**Verdict:** READY FOR USER APPROVAL. Remaining decisions requiring approval are in §17.

### §3D. State-Transition Table

| Current state | Trigger | New state | Condition |
|---|---|---|---|
| PENDING_CONFIRMATION | Confirm endpoint | PROCESSING | `expires_at > now()` |
| PENDING_CONFIRMATION | Any read (lazy) | EXPIRED | `expires_at ≤ now()` |
| PROCESSING | Import completes, no STARTED/uncertain, `imported = valid_count` | COMPLETED | `uncertain = 0`, all rows definitive |
| PROCESSING | Import completes, no STARTED/uncertain, `0 < imported < valid_count` | PARTIALLY_COMPLETED | `uncertain = 0`, all rows definitive |
| PROCESSING | Import completes, no STARTED/uncertain, `imported = 0` | FAILED | `uncertain = 0`, all rows definitive |
| PROCESSING | Import interrupted, STARTED rows or uncertain remain | PROCESSING (stays) | No terminal write; heartbeat goes stale |
| PROCESSING | Reconciliation claim | RECONCILING | heartbeat stale (> P1 threshold) |
| RECONCILING | Reconciliation finishes | COMPLETED / PARTIALLY_COMPLETED / FAILED | Token matches, `uncertain = 0`, all rows definitive |
| RECONCILING | Re-claim | RECONCILING | `reconciliation_started_at` stale (> P15 threshold), new token |

**Disallowed transitions:** EXPIRED, COMPLETED, PARTIALLY_COMPLETED, FAILED → anything. PROCESSING → EXPIRED. RECONCILING → PROCESSING.

**Key invariant:** No terminal state is reachable with `uncertain_count > 0` or any STARTED child rows. If the import loop has unresolved rows, it does NOT write terminal status. The session stays PROCESSING for reconciliation.

### §4.3. `was_attempted` column semantics

| Value | Meaning | Set by |
|---|---|---|
| `TRUE` | Registration function was definitely invoked for this row. | T3 (SUCCEEDED, FAILED, OUTCOME_UNCERTAIN) |
| `FALSE` | Registration function was definitely never invoked. | After-loop (never-started rows); reconciliation (no child row + no audit) |
| `NULL` | Whether registration was invoked cannot be determined. | T1 (initial); reconciliation (STARTED child + no audit) |

**Rationale:** When reconciliation resolves a STARTED child row with no audit record, the row is classified NOT_PROCESSED (no student exists). But the system cannot determine whether `register_student()` was called and rolled back (attempt occurred, then lost) or was never called (crash before T2). Setting `was_attempted = NULL` is honest; FALSE would claim certainty the system does not possess.

## §5. CSV Parsing and Preview Behavior

### §5.1. File acceptance (content-based, not MIME-based)

The upload endpoint reads up to 5,000,001 bytes from the uploaded file. If more data remains, return 413 immediately without buffering the entire file.

Acceptance is determined by content, not MIME type or extension:

1. **UTF-8 decode.** Attempt `bytes.decode('utf-8')`. Strip leading BOM (U+FEFF) if present. Decode failure → 422 "File is not valid UTF-8."
2. **Strict CSV parse.** Use Python's `csv.reader` with `strict=True`. Set `csv.field_size_limit(8192)` before parsing. Any `csv.Error` → 422 with the parser's error message.
3. **Header validation.** See §5.2.
4. **Column-count consistency.** Every non-blank data record must have exactly the same number of fields as the header row. A mismatch → 400 "Record N has M fields, expected K."
5. **Data record count.** Count non-blank data records (§5.3). Zero → 400 "No data records." More than 100 → 400 "Maximum 100 data records."

### §5.2. Header validation

Required (case-insensitive, trimmed): `first_name`, `last_name`, `email`, `roll_number`, `program_code`, `semester_level`, `admission_term`.

Optional: `section_name`, `phone`, `address`.

Rejections: missing required → 400; duplicate (case-insensitive) → 400; unknown → 400.

### §5.3. Record numbering and blank-row handling

**Definitions:**

- A **CSV record** is one logical record as parsed by `csv.reader`. A record may span multiple physical lines if it contains a quoted field with embedded newlines.
- A **blank record** is one where every field is empty after stripping whitespace.
- `csv_record_number` is the **1-indexed ordinal of non-blank data records**, counting sequentially from the first record after the header. Blank records are skipped and do not receive a number.

**Example with multi-line quoted field:**

```csv
first_name,last_name,email,roll_number,program_code,semester_level,admission_term,address
Ahmad,Khan,a@x.com,CS-001,BSCS,1,Fall 2026,"123 Main St
Apt 4B"
Sara,Ali,s@x.com,CS-002,BSCS,1,Fall 2026,456 Oak Ave
```

Record 1 (Ahmad) spans physical lines 2–3 but is one CSV record. `csv_record_number = 1`.
Record 2 (Sara) is on physical line 4. `csv_record_number = 2`.

**`valid_row_index`** is assigned to records that pass all preview validations, numbered sequentially from 1 through `valid_count` in `csv_record_number` order.

`valid_row_index` is used for: processing order, T1 progress tracking, child-table uniqueness, reconciliation, finding unprocessed rows.

`csv_record_number` is preserved for: preview display, results display, downloadable report.

### §5.4. Column-aware formula-cell validation

**Formula-trigger characters:** `= @ \t \r \n`

**Checked columns:** `first_name`, `last_name`, `email`, `roll_number`, `program_code`, `semester_level`, `admission_term`, `section_name`, `address`.

**Exempt column:** `phone` — valid E.164 numbers start with `+`. The existing `normalize_phone()` at [validators.py:95–125](backend/app/modules/students/validators.py#L95-L125) rejects non-phone values (`+SUM(1,2)` fails `^\+[1-9][0-9]{7,14}$`).

**Rules for checked columns:**
1. First character in `{= @ \t \r \n}` → reject: `FORMULA_CELL`.
2. First character is `+` or `-` → reject: `FORMULA_CELL`.
3. First non-whitespace character (after leading spaces) is in `{= + - @}` → reject: `FORMULA_CELL`.

### §5.5. Semester-level validation

Parse `semester_level` as an integer. Reject non-integer values. Check `≥ 1` as a minimum sanity check.

After resolving the program via `program_code`, check `semester_level ≤ program.duration_semesters`. This is the existing Phase 4 business rule at [service.py:734](backend/app/modules/students/service.py#L734). No arbitrary upper cap in CSV code — the bound comes from the resolved program.

The database backstops `ck_student_placements_level BETWEEN 1 AND 16` and `ck_programs_duration_semesters BETWEEN 1 AND 16` remain unchanged.

### §5.6. Academic reference resolution

Exact match only, no fuzzy matching:
- `program_code` → `lower(code) = lower(input)` against active programs in the target department.
- `admission_term` → `derive_term_name()` comparison against non-archived terms. Case-insensitive, trimmed.
- `section_name` → `lower(name)` match against active sections of the resolved program at the given `semester_level`. Optional.

### §5.7. `preview_invalid_results`

Stored at upload time. Contains PII-free error summaries for invalid records:

```json
[
  {
    "csv_record_number": 7,
    "errors": [
      {"field": "email", "code": "REQUIRED", "message": "Email is required."},
      {"field": "semester_level", "code": "OUT_OF_RANGE",
       "message": "Semester level must be between 1 and 8 for this program."}
    ]
  }
]
```

No original cell values, email, phone, address, or names. Never scrubbed. Immutable after upload.

### §5.8. `expires_at`

Set at upload: `created_at + INTERVAL '30 minutes'`. Immutable after upload (not in UPDATE grants).

### §5.9. Strict parsing summary

| Concern | Behavior |
|---------|----------|
| File > 5 MB | 413 — rejected before full read |
| Not UTF-8 | 422 |
| BOM present | Stripped silently |
| `strict=True` | Malformed quoting → 422 |
| `field_size_limit(8192)` | Any field > 8 KB → 422 |
| Inconsistent column count | 400 with record number |
| All-blank records | Skipped, no record number assigned |
| Embedded newlines in quoted fields | Valid CSV; one record, one `csv_record_number` |
| > 100 non-blank records | 400 |
| 0 non-blank records | 400 |

## §6. Confirmation and Transaction Boundaries

### §6.1. Confirmation claim

```sql
UPDATE bulk_upload_sessions
SET status = 'PROCESSING',
    confirmed_by_user_id = :actor_id,
    confirmed_at = now(),
    processing_started_at = now(),
    processing_heartbeat_at = now(),
    updated_at = now()
WHERE id = :upload_id
  AND status = 'PENDING_CONFIRMATION'
  AND expires_at > now()
RETURNING id;
```

0 rows → check actual status: if PENDING_CONFIRMATION with `expires_at ≤ now()` → lazily transition to EXPIRED, return 409; if other state → 409; if not found → 404.

Audit event `bulk_import.confirmed` is recorded via `AuditService.record()` (flush only) in the same transaction as this UPDATE. The caller commits both atomically.

### §6.2. Lazy expiry

On any read of a PENDING_CONFIRMATION session with `expires_at ≤ now()`:

```sql
UPDATE bulk_upload_sessions
SET status = 'EXPIRED',
    validated_rows = '[]',
    updated_at = now()
WHERE id = :upload_id
  AND status = 'PENDING_CONFIRMATION'
  AND expires_at <= now();
```

No background worker. Expiry is detected on access only.

### §6.3. Audit event transaction boundaries

| Event | Transaction boundary |
|-------|---------------------|
| `bulk_import.uploaded` | Same transaction as the INSERT of `bulk_upload_sessions` |
| `bulk_import.confirmed` | Same transaction as the confirmation UPDATE |
| `bulk_import.completed` | Same transaction as the terminal status UPDATE + `validated_rows` scrub |
| `bulk_import.interrupted` | After-loop transaction (session remains PROCESSING; see §9.4 and §14) |
| `bulk_import.reconciled` | Same transaction as the reconciliation terminal UPDATE (see §10) |

Each uses `AuditService.record()`, which calls `flush()` only. The caller's `db.commit()` commits both the state change and the audit record atomically.

**Interruption specifics (correction 4):** The `bulk_import.interrupted` event does NOT share a transaction with any terminal status write, because no terminal write occurs when STARTED or uncertain rows remain. It is committed in the after-loop transaction that also inserts NOT_PROCESSED child rows for never-started indexes. See §9.4 for details.

## §7. Durable Row-Progress Model: T1, T2, T3 Transaction Boundaries

### §7.1. T1 — STARTED child row (safe for existing rows)

```
T1 for valid_row_index = I, csv_record_number = R:

  INSERT INTO bulk_upload_row_results
    (upload_session_id, valid_row_index, csv_record_number, status, was_attempted)
    VALUES (:session_id, I, R, 'STARTED', NULL)
    ON CONFLICT (upload_session_id, valid_row_index) DO NOTHING
    RETURNING id

  IF RETURNING yields a row (new insert):
    UPDATE bulk_upload_sessions
      SET last_started_valid_index = I,
          processing_heartbeat_at = now(),
          updated_at = now()
      WHERE id = :session_id AND status = 'PROCESSING'
    IF session UPDATE rowcount = 0 → ROLLBACK → result: FENCED
    ELSE → COMMIT → result: PROCEED

  IF RETURNING yields no rows (conflict — row already exists):
    ROLLBACK → result: SKIP
```

**Conflict behavior by existing child-row status:**

| Existing status | T1 action | T2 called? | Rationale |
|---|---|---|---|
| STARTED | SKIP | No | May be from a lost-ACK T1 retry, or T2 may have been attempted. Reconciliation will inspect audit to determine outcome. |
| SUCCEEDED | SKIP | No | Already processed. Student exists. |
| FAILED | SKIP | No | Already processed. Business error recorded. |
| NOT_PROCESSED | SKIP | No | Already classified by prior after-loop or reconciliation. |
| OUTCOME_UNCERTAIN | SKIP | No | Already classified. Reconciliation will resolve. |

**Proof that ON CONFLICT DO NOTHING cannot reset progress or permit duplicate registration:**

1. `DO NOTHING` does not modify any column of the existing row. The existing status, student_id, error info, was_attempted — all untouched.
2. When conflict is detected (RETURNING yields no rows), the importer skips the row entirely. `register_student()` is never called for this row. No duplicate registration can occur.
3. The heartbeat and `last_started_valid_index` are NOT updated for skipped rows (the INSERT was a no-op, so the parent UPDATE is never reached).

### §7.2. T2 — Registration

```
T2: register_student(
      ...,
      bulk_origin=BulkImportOrigin(session_id, I)
    )

  Internally:
    FOR SHARE on bulk_upload_sessions (fencing check — §8)
    _lock_and_validate() (FOR SHARE on term, department, program, section)
    Create User, Student, Placement
    AuditService.record() — flush only
    COMMIT (line 309) — student + audit durable

  OR: ROLLBACK + raise (lines 248, 311, 322)
```

T2 is `register_student()`'s internal transaction. It commits or rolls back independently. The import loop does not control this transaction boundary.

### §7.3. T3 — Outcome persistence (child + parent atomic)

```
T3 for valid_row_index = I:

  BEGIN (implicit — SQLAlchemy session after T2's commit/rollback is clean)

  UPDATE bulk_upload_row_results
    SET status = :outcome,
        student_id = :sid,
        was_attempted = TRUE,
        first_name = :fn, last_name = :ln, roll_number = :rn,
        error_code = :ec, error_message = :em,
        corrective_action = :ca, is_retryable = :ir,
        updated_at = now()
    WHERE upload_session_id = :session_id
      AND valid_row_index = I
      AND status = 'STARTED'

  child_rowcount = affected rows

  IF child_rowcount = 1:
    -- Normal path: update parent counter + heartbeat
    UPDATE bulk_upload_sessions
      SET <counter>_count = <counter>_count + 1,
          processing_heartbeat_at = now(),
          updated_at = now()
      WHERE id = :session_id AND status = 'PROCESSING'

    IF session UPDATE rowcount = 0:
      ROLLBACK → result: FENCED (child update also rolled back)
    ELSE:
      COMMIT → result: OK

  IF child_rowcount = 0:
    -- Child row not in STARTED state — verify consistency
    existing_status = SELECT status FROM bulk_upload_row_results
      WHERE upload_session_id = :session_id AND valid_row_index = I

    IF existing_status IS NULL:
      -- Child row missing entirely (should not happen — T1 creates it)
      ROLLBACK
      Log error: "Child row missing for index I"
      result: INCONSISTENT

    ELSE IF existing_status = :intended_outcome:
      -- Idempotent: T3 previously committed but ACK was lost.
      -- Counter was already incremented. No action needed.
      ROLLBACK (discard the read-only transaction)
      result: ALREADY_WRITTEN

    ELSE:
      -- Existing status does not match intended outcome.
      -- This indicates a bug or unexpected concurrent modification.
      ROLLBACK
      Log error: "Child row I has status <existing> but intended <outcome>"
      result: INCONSISTENT
```

**Key properties:**
- Child UPDATE and parent counter UPDATE are in the **same transaction**. If the parent UPDATE fails (fencing or other error), ROLLBACK undoes both.
- When child UPDATE returns 0 rows, the existing status is read and verified. Silent acceptance of any zero-row result is never permitted.
- `ALREADY_WRITTEN` result means the loop continues safely (no double-counting).
- `INCONSISTENT` result means the loop enters INTERRUPTED state.

### §7.4. T1, T2, T3 independence

T1, T2, and T3 are three independent committed transactions on the same SQLAlchemy session. Between each, the session is clean (committed or rolled back). The SQLAlchemy session's `autoflush=False` and `expire_on_commit=False` settings ensure no surprise flushes or state expirations.

### §7.5. Crash-window analysis (every transaction boundary)

| # | Crash point | Child-row state | Audit exists? | Parent counter updated? | Recovery path |
|---|---|---|---|---|---|
| CW1 | After upload INSERT, before COMMIT | — | No | — | Upload failed; client retries. No session exists. |
| CW2 | After upload COMMIT | — | Yes (uploaded) | — | Normal flow continues. |
| CW3 | After confirm UPDATE, before import loop starts | — | Yes (confirmed) | — | Session PROCESSING, heartbeat stale → reconcile (0 rows processed, all NOT_PROCESSED). |
| CW4 | T1 INSERT committed, ACK lost | STARTED | No | heartbeat updated | App gets connection error → INTERRUPTED → after-loop fails (broken session) → session stays PROCESSING → reconcile: STARTED + no audit → NOT_PROCESSED. |
| CW5 | After T1 COMMIT, before T2 starts | STARTED | No | heartbeat updated | INTERRUPTED → after-loop inserts NOT_PROCESSED for unstarted rows, leaves STARTED → reconcile: STARTED + no audit → NOT_PROCESSED. |
| CW6 | During T2, before its COMMIT | STARTED | No | heartbeat from T1 | Same as CW5. T2 rolls back (no student). |
| CW7 | T2 COMMIT sent, ACK lost | STARTED | Maybe | heartbeat from T1 | App doesn't know if committed. persist_uncertain() may fail. INTERRUPTED → reconcile: if audit → SUCCEEDED; if no audit → NOT_PROCESSED (was_attempted=NULL). |
| CW8 | After T2 COMMIT (success), before T3 | STARTED | Yes | heartbeat from T1 | INTERRUPTED → after-loop leaves STARTED → reconcile: STARTED + audit → SUCCEEDED. |
| CW9 | After T2 ROLLBACK (business error), before T3 | STARTED | No | heartbeat from T1 | INTERRUPTED → after-loop leaves STARTED → reconcile: STARTED + no audit → NOT_PROCESSED (was_attempted=NULL). Lost error details are irrecoverable. |
| CW10 | T3 child+parent UPDATE committed, ACK lost | Final status | Yes (if SUCCEEDED) | Yes | App gets error. Session may be broken → INTERRUPTED → after-loop: T1 for next row would see existing final child row → SKIP. Or if loop breaks: reconcile uses child-row status as-is. |
| CW11 | After T3 COMMIT | Final status | Matches | Yes | Normal flow. |
| CW12 | After all rows, before after-loop runs | All children final or STARTED | Per-row | Per-row | INTERRUPTED (if loop broke) or NORMAL. After-loop or reconcile handles. |
| CW13 | After-loop transaction committed, ACK lost | Children classified | Audit maybe | Counters maybe | If committed: session is terminal or PROCESSING with interrupted audit. If not: reconcile handles. |
| CW14 | Terminal write COMMIT sent, ACK lost | All final | All present | All counted | If committed: session is terminal, validated_rows scrubbed. If not: session stays PROCESSING → reconcile. |

## §8. Registration Fencing and Lock Ordering

### §8.1. Lock ordering

```
bulk_upload_sessions (FOR SHARE)  ← only when bulk_origin provided
  → term (FOR SHARE)
    → department (FOR SHARE)
      → program (FOR SHARE)
        → section (FOR SHARE)
          → student (FOR UPDATE)       ← correction only
            → placement (FOR UPDATE)   ← correction only
```

No existing code locks `bulk_upload_sessions` (new table). Reconciliation's UPDATE acquires an exclusive lock on `bulk_upload_sessions` only. No cycle is possible.

### §8.2. FOR SHARE inside register_student()

New parameter: `bulk_origin: BulkImportOrigin | None = None`.

```python
@dataclass(frozen=True)
class BulkImportOrigin:
    upload_session_id: uuid.UUID
    row_index: int  # valid_row_index, for audit metadata
```

Inside the first try block of `register_student()`, before `_lock_and_validate()`:

```python
if bulk_origin is not None:
    session_status = self.db.scalar(
        select(BulkUploadSession.status)
        .where(BulkUploadSession.id == bulk_origin.upload_session_id)
        .with_for_update(read=True)  # FOR SHARE
    )
    if session_status != BulkUploadStatus.PROCESSING.value:
        raise BulkImportSessionFencedError(
            "Import session is no longer active."
        )
```

Lock is held until `self.db.commit()` (line 309) or `self.db.rollback()` (lines 248, 311, 322).

### §8.3. Fencing invariant

No student can be committed after reconciliation claims the session without reconciliation seeing the audit record.

**Case 1 — Registration commits first:** FOR SHARE acquired → reconciliation's claim UPDATE blocks (FOR SHARE and UPDATE are incompatible at the row level in PostgreSQL). After registration commits, lock released, audit visible. Reconciliation proceeds and sees the audit record.

**Case 2 — Reconciliation claims first:** Reconciliation's claim UPDATE acquires an implicit exclusive lock on the session row. The registration's FOR SHARE blocks until reconciliation commits. After reconciliation commits (session is terminal), FOR SHARE reads the terminal status → `BulkImportSessionFencedError` → rollback → no student created.

**Case 3 — Connection lost:** PostgreSQL rolls back the transaction holding the lock → lock released. No student committed if registration hadn't reached its COMMIT; reconciliation proceeds normally.

## §9. Import-Loop State Machine, Exception Handling, and After-Loop Algorithm

### §9.1. `BulkImportSessionFencedError`

```python
class BulkImportSessionFencedError(StudentServiceError):
    """Raised when the bulk upload session is no longer PROCESSING.
    NOT a subclass of StudentConflictError — must not be caught
    by the business-error handler in the import loop."""
```

### §9.2. ImporterState enum

```python
class ImporterState(StrEnum):
    NORMAL = "NORMAL"           # processing rows
    FENCED = "FENCED"           # session claimed by reconciliation
    INTERRUPTED = "INTERRUPTED" # unexpected error, cannot continue
```

### §9.3. Import loop with explicit state transitions

```python
importer_state = ImporterState.NORMAL

for vr in valid_rows:
    index = vr["valid_row_index"]
    csv_record = vr["csv_record_number"]

    # ── T1: STARTED ──
    t1_result = persist_started(db, session_id, index, csv_record)

    if t1_result == T1Result.FENCED:
        importer_state = ImporterState.FENCED
        break

    if t1_result == T1Result.SKIP:
        # Child row already exists. Do not process.
        continue

    # t1_result == T1Result.PROCEED — fresh child row created

    try:
        result = student_service.register_student(
            actor=actor, department_id=department_id,
            data=make_registration_data(vr),
            ip_address=ip_address,
            bulk_origin=BulkImportOrigin(session_id, index),
        )

        # ── T3: SUCCEEDED ──
        t3_result = persist_outcome(
            db, session_id, index,
            outcome=RowOutcome.SUCCEEDED,
            student_id=result.student.id,
            first_name=result.user.first_name,
            last_name=result.user.last_name,
            roll_number=result.student.roll_number,
        )

        if t3_result == T3Result.FENCED:
            importer_state = ImporterState.FENCED
            break
        if t3_result == T3Result.INCONSISTENT:
            importer_state = ImporterState.INTERRUPTED
            break

        schedule_email(background_tasks, ...)

    except BulkImportSessionFencedError:
        importer_state = ImporterState.FENCED
        break

    except (StudentConflictError, StudentValidationError,
            StudentReferenceNotFoundError) as exc:

        # ── T3: FAILED ──
        t3_result = persist_outcome(
            db, session_id, index,
            outcome=RowOutcome.FAILED,
            error_code=classify_error(exc),
            error_message=str(exc),
            corrective_action=suggest_correction(exc),
            is_retryable=is_retryable(exc),
            first_name=vr.get("first_name"),
            last_name=vr.get("last_name"),
            roll_number=vr.get("roll_number"),
        )

        if t3_result == T3Result.FENCED:
            importer_state = ImporterState.FENCED
            break
        if t3_result == T3Result.INCONSISTENT:
            importer_state = ImporterState.INTERRUPTED
            break

    except Exception:
        # ── T3: OUTCOME_UNCERTAIN ──
        try:
            persist_outcome(
                db, session_id, index,
                outcome=RowOutcome.OUTCOME_UNCERTAIN,
                first_name=vr.get("first_name"),
                last_name=vr.get("last_name"),
                roll_number=vr.get("roll_number"),
            )
        except Exception:
            pass  # child row stays STARTED; reconciliation handles it
        importer_state = ImporterState.INTERRUPTED
        break
```

### §9.4. After-loop algorithm (all three states)

**This is the corrected algorithm that never reclassifies STARTED rows.**

```python
if importer_state == ImporterState.FENCED:
    # ═══ FENCED ═══
    # Session is in RECONCILING (or about to be claimed).
    # Do NOT classify any remaining rows.
    # Do NOT write terminal status.
    # Do NOT write any audit events.
    # Leave everything for the reconciler.
    pass

elif importer_state in (ImporterState.NORMAL, ImporterState.INTERRUPTED):
    # ═══ NORMAL or INTERRUPTED ═══

    try:
        # Step 1: Find valid_row_indexes with NO child row at all.
        # These are rows the import loop never reached (never started).
        # They can safely be classified as NOT_PROCESSED.
        existing_indexes = set(
            db.scalars(
                select(BulkUploadRowResult.valid_row_index)
                .where(BulkUploadRowResult.upload_session_id == session_id)
            ).all()
        )
        all_indexes = set(range(1, valid_count + 1))
        never_started_indexes = all_indexes - existing_indexes

        # Step 2: Insert NOT_PROCESSED child rows for never-started indexes.
        for mi in sorted(never_started_indexes):
            csv_rec = index_to_csv_record[mi]  # from in-memory mapping
            db.execute(
                insert(BulkUploadRowResult).values(
                    upload_session_id=session_id,
                    valid_row_index=mi,
                    csv_record_number=csv_rec,
                    status=RowOutcome.NOT_PROCESSED.value,
                    was_attempted=False,
                )
            )

        # Step 3: Count unresolved rows (STARTED or OUTCOME_UNCERTAIN).
        unresolved_count = db.scalar(
            select(func.count())
            .where(BulkUploadRowResult.upload_session_id == session_id)
            .where(BulkUploadRowResult.status.in_([
                RowOutcome.STARTED.value,
                RowOutcome.OUTCOME_UNCERTAIN.value,
            ]))
        )

        if unresolved_count > 0:
            # Step 4a: STARTED or OUTCOME_UNCERTAIN rows remain.
            # Do NOT terminalize. Session stays PROCESSING.
            # Record the interrupted audit event in this transaction.
            audit_service.record(
                action=AuditAction.BULK_IMPORT_INTERRUPTED,
                entity_type=AuditEntityType.BULK_UPLOAD_SESSION,
                entity_id=session_id,
                actor_user_id=actor.id,
                metadata={
                    "unresolved_count": unresolved_count,
                    "imported_count": current_imported,
                    "failed_count": current_failed,
                },
                ip_address=ip_address,
            )
            # Update counters to reflect the NOT_PROCESSED inserts,
            # but do NOT clear uncertain_count or write terminal status.
            db.execute(
                update(BulkUploadSession)
                .where(BulkUploadSession.id == session_id)
                .where(BulkUploadSession.status == BulkUploadStatus.PROCESSING.value)
                .values(
                    not_processed_count=len(never_started_indexes)
                        + current_not_processed,
                    updated_at=func.now(),
                )
            )
            db.commit()
            # Session stays PROCESSING. Heartbeat goes stale.
            # Reconciliation resolves STARTED/OUTCOME_UNCERTAIN rows.

        else:
            # Step 4b: All rows have definitive outcomes (no STARTED, no UNCERTAIN).
            # Verify total count matches valid_count.
            definitive_count = db.scalar(
                select(func.count())
                .where(BulkUploadRowResult.upload_session_id == session_id)
                .where(BulkUploadRowResult.status.in_([
                    RowOutcome.SUCCEEDED.value,
                    RowOutcome.FAILED.value,
                    RowOutcome.NOT_PROCESSED.value,
                ]))
            )
            if definitive_count != valid_count:
                # Count mismatch — do not terminalize.
                db.rollback()
                # Session stays PROCESSING → reconciliation.
            else:
                # Recalculate counters from child table.
                counts = recalculate_counts(db, session_id)
                terminal_status = determine_terminal_status(counts)
                db.execute(
                    update(BulkUploadSession)
                    .where(BulkUploadSession.id == session_id)
                    .where(BulkUploadSession.status ==
                           BulkUploadStatus.PROCESSING.value)
                    .values(
                        status=terminal_status.value,
                        imported_count=counts.succeeded,
                        failed_count=counts.failed,
                        not_processed_count=counts.not_processed,
                        uncertain_count=0,
                        validated_rows=text("'[]'::jsonb"),
                        completed_at=func.now(),
                        updated_at=func.now(),
                    )
                )
                audit_service.record(
                    action=AuditAction.BULK_IMPORT_COMPLETED,
                    entity_type=AuditEntityType.BULK_UPLOAD_SESSION,
                    entity_id=session_id,
                    actor_user_id=actor.id,
                    metadata={"status": terminal_status.value, **counts._asdict()},
                    ip_address=ip_address,
                )
                db.commit()

    except Exception:
        # After-loop itself failed (e.g., DB connection lost).
        # Nothing is committed. Session stays PROCESSING.
        # get_db()'s finally: db.close() cleans up.
        try:
            db.rollback()
        except Exception:
            pass
        # Session stays PROCESSING → heartbeat stale → reconciliation.
```

**Critical safety properties of this algorithm:**

1. **STARTED rows are never reclassified.** Step 2 only inserts for `never_started_indexes` (indexes with NO child row at all). Existing STARTED rows are untouched.
2. **STARTED rows block terminalization.** Step 3 counts STARTED and OUTCOME_UNCERTAIN rows. If `unresolved_count > 0`, step 4a runs: no terminal status, session stays PROCESSING.
3. **Terminal write is conditional on completeness.** Step 4b verifies `definitive_count == valid_count` before writing terminal status.
4. **After-loop failure is safe.** If the try block fails, nothing is committed. Session stays PROCESSING with stale heartbeat.

### §9.5. Behavior when database connection is unavailable

If the connection is lost mid-import:

1. The current transaction (T1, T2, or T3) fails with a connection error.
2. The importer catches it as an unexpected exception → `importer_state = INTERRUPTED`.
3. The after-loop attempts to run but all DB operations fail (no connection).
4. The `except Exception` at the end of the after-loop catches the failure.
5. `db.rollback()` may also fail (no connection) — caught and ignored.
6. `get_db()`'s `finally: db.close()` runs, releasing the broken connection.
7. The confirm endpoint returns 500 (the connection error propagates).
8. The session stays PROCESSING with stale heartbeat.
9. Reconciliation (triggered by a future request on a healthy connection) resolves all rows.

### §9.6. Behavior when the SQLAlchemy session cannot be reused

If a failed rollback puts the session in an error state:

1. Any subsequent `db.execute()` or `db.scalar()` raises `InvalidRequestError`.
2. The importer enters INTERRUPTED and breaks immediately.
3. The after-loop attempts to run but every DB call raises `InvalidRequestError`.
4. The `except Exception` catches everything.
5. `get_db()`'s `finally: db.close()` cleans up the session object.
6. Session stays PROCESSING with stale heartbeat → reconciliation.

**Key safety property:** A broken import loop can never leave the system in an inconsistent state. The worst case is "session stuck in PROCESSING with stale heartbeat," which reconciliation handles.

## §10. Reconciliation: Single-Transaction Ownership Model

### §10.1. Transaction strategy

The entire reconciliation — claim, child-row reads, audit query, child-row mutations, counter recalculation, terminal write, `validated_rows` scrubbing, and audit — runs in a **single database transaction**.

The claim UPDATE implicitly acquires a **row-level exclusive lock** on the `bulk_upload_sessions` row. This lock is held until COMMIT or ROLLBACK. While held:

- No other reconciler's claim UPDATE can proceed (it blocks on the row lock).
- The import loop's FOR SHARE on the same row also blocks (FOR SHARE and exclusive lock are incompatible).
- After this transaction commits (session is terminal), any blocked FOR SHARE reads the terminal status and raises `BulkImportSessionFencedError`.

The `reconciliation_claim_token` remains as **defense-in-depth** on the final terminal UPDATE. In practice, the row lock prevents concurrent claims, but the token guards against implementation bugs.

### §10.2. Claim (within the single transaction)

```sql
BEGIN;
SET LOCAL lock_timeout = '10s';

UPDATE bulk_upload_sessions
SET status = 'RECONCILING',
    reconciliation_claimed_by = :actor_id,
    reconciliation_started_at = now(),
    reconciliation_claim_token = :new_token,
    updated_at = now()
WHERE id = :upload_id
  AND (
    (status = 'PROCESSING'
     AND processing_heartbeat_at < now() - INTERVAL '5 minutes')
    OR
    (status = 'RECONCILING'
     AND reconciliation_started_at < now() - INTERVAL '5 minutes')
  )
RETURNING id, reconciliation_claim_token, valid_count;
```

`:new_token` = `uuid.uuid4()` generated per claim.

Lock timeout hit → ROLLBACK, return 503. 0 rows → ROLLBACK, return 409.

### §10.3. Algorithm (same transaction continues)

**Step 1 — Read child rows:**

```sql
SELECT valid_row_index, status, student_id
FROM bulk_upload_row_results
WHERE upload_session_id = :upload_id;
```

Build a map: `{valid_row_index → (status, student_id)}`.

**Step 2 — Read `validated_rows`** (not yet scrubbed) for the `valid_row_index → csv_record_number` mapping.

**Step 3 — Query audit records:**

```sql
SELECT entity_id,
       (event_metadata->>'bulk_upload_row_number')::integer AS row_index
FROM audit_logs
WHERE action = 'student.registered'
  AND event_metadata->>'bulk_upload_session_id' = :upload_id_text;
```

Build a map: `{row_index → entity_id (student_id)}`.

**Step 4 — Classify every valid row** (index 1..valid_count):

| Child-row state | Audit record? | Classification | `was_attempted` |
|---|---|---|---|
| SUCCEEDED | Verify present | SUCCEEDED (keep) | TRUE (keep) |
| FAILED | Verify absent | FAILED (keep) | TRUE (keep) |
| NOT_PROCESSED | Verify absent | NOT_PROCESSED (keep) | Keep existing |
| OUTCOME_UNCERTAIN | Yes | → SUCCEEDED | TRUE |
| OUTCOME_UNCERTAIN | No | → NOT_PROCESSED | NULL |
| STARTED | Yes | → SUCCEEDED | TRUE |
| STARTED | No | → NOT_PROCESSED | NULL |
| No child row | Yes | Create SUCCEEDED row | TRUE |
| No child row | No | Create NOT_PROCESSED row | FALSE |

**Step 5 — Apply changes** (all within the same transaction):

- **Update child rows** where classification changed (STARTED → SUCCEEDED, OUTCOME_UNCERTAIN → NOT_PROCESSED, etc.).
- **Insert child rows** for indexes that had no child row.

**Step 6 — Recalculate counters** from child table:

```sql
SELECT status, COUNT(*)
FROM bulk_upload_row_results
WHERE upload_session_id = :upload_id
GROUP BY status;
```

Verify: total count = valid_count. No STARTED or OUTCOME_UNCERTAIN rows remain.

**Step 7 — Terminal write with ownership token (defense-in-depth):**

```sql
UPDATE bulk_upload_sessions
SET status = :terminal,
    imported_count = :c1,
    failed_count = :c2,
    not_processed_count = :c3,
    uncertain_count = 0,
    validated_rows = '[]',
    completed_at = now(),
    was_reconciled = TRUE,
    updated_at = now()
WHERE id = :upload_id
  AND status = 'RECONCILING'
  AND reconciliation_claim_token = :my_token
RETURNING id;
```

0 rows → data inconsistency (should not happen with single-transaction model). Log error, ROLLBACK.

**Step 8 — Audit record:**

```python
audit_service.record(
    action=AuditAction.BULK_IMPORT_RECONCILED,
    entity_type=AuditEntityType.BULK_UPLOAD_SESSION,
    entity_id=session_id,
    actor_user_id=actor.id,
    metadata={...},
    ip_address=ip_address,
)
```

**Step 9 — COMMIT.**

All child-row mutations, counter updates, terminal status, `validated_rows` scrubbing, and audit record are committed atomically. If COMMIT fails, everything rolls back. The session reverts to its pre-claim state (PROCESSING or previous RECONCILING), and the row lock is released.

### §10.4. Why a single transaction prevents stale-reconciler mutations

**Scenario:** Reconciler A claims first, reconciler B tries to re-claim.

1. A's transaction begins. A's claim UPDATE acquires exclusive row lock on the session row.
2. B's claim UPDATE blocks on the row lock.
3. B waits up to 10 seconds (`lock_timeout`).

**Case A finishes first (within 10s):**
4. A commits → session is now terminal (COMPLETED/PARTIALLY_COMPLETED/FAILED) → row lock released.
5. B's UPDATE proceeds. The WHERE clause checks `status = 'PROCESSING' AND heartbeat stale OR status = 'RECONCILING' AND started stale`. Session is now terminal → neither condition matches → 0 rows → B returns 409.
6. **B has never modified any child rows.** B's entire transaction consisted of one blocked UPDATE that matched nothing.

**Case A is slow (B times out):**
4. B's lock_timeout expires → B gets an error → B returns 503 → B's transaction rolls back.
5. A eventually finishes and commits.
6. **B has never modified any child rows.** B's transaction rolled back before it could do anything.

**Case A's connection drops:**
4. PostgreSQL detects the broken connection → A's transaction rolls back automatically.
5. All of A's child-row mutations are undone.
6. Row lock released.
7. B's UPDATE proceeds. Session is back to PROCESSING (or previous RECONCILING) with stale heartbeat → B's claim succeeds.
8. B runs the full algorithm from scratch on the original (pre-A) child-row state.

**In all cases, at most one reconciler's child-row mutations are committed.**

### §10.5. Interaction with concurrent registration (FOR SHARE)

If a late `register_student()` T2 is in-flight when reconciliation starts:

- T2 holds FOR SHARE on the session row.
- Reconciliation's claim UPDATE needs an exclusive lock.
- Exclusive lock is incompatible with FOR SHARE → reconciliation blocks.
- T2 commits (student + audit) → FOR SHARE released.
- Reconciliation proceeds. The audit record from T2 is now visible.
- Reconciliation correctly classifies the row as SUCCEEDED.

If reconciliation claims first (exclusive lock acquired) and T2 tries FOR SHARE:

- T2 blocks until reconciliation commits.
- After commit, session is terminal → T2's FOR SHARE reads terminal status → `BulkImportSessionFencedError` → T2 rolls back → no student.

## §11. Outcome Semantics and Count Invariants

### §11.1. Outcome definitions

| Outcome | Meaning | `was_attempted` | Student created? |
|---|---|---|---|
| SUCCEEDED | Audit record confirms student was created and committed. | TRUE | Yes |
| FAILED | Registration was invoked, raised a known business error, the error was durably recorded, and no student was created. | TRUE | No |
| NOT_PROCESSED | No durable evidence that a student was created for this row. Set by after-loop for rows never started (no child row). Set by reconciliation for STARTED rows with no audit record. The import function may or may not have been invoked — the system cannot determine this. | FALSE (never started) or NULL (indeterminate) | No |
| OUTCOME_UNCERTAIN | Registration was invoked but an unexpected error occurred. The outcome has not yet been resolved. Set only by the import loop. Resolved by reconciliation to SUCCEEDED or NOT_PROCESSED. | TRUE | Unknown until resolved |
| SKIPPED_PREVIEW_INVALID | Failed preview validation. Never attempted. | — (not in child table) | No |

**Honest classification of lost failure details (correction 1 scenario):**

1. T1 commits STARTED.
2. T2 commits student + audit.
3. Connection lost before T3.
4. persist_uncertain() fails (no connection).
5. Importer enters INTERRUPTED.
6. After-loop: finds STARTED child row for this index → **leaves it untouched** (never reclassifies STARTED).
7. After-loop: `unresolved_count > 0` → no terminal write → session stays PROCESSING.
8. Reconciliation: reads STARTED child row + finds audit record → classifies as SUCCEEDED (`was_attempted = TRUE`).

The student is correctly accounted for. No false NOT_PROCESSED.

**Contrast with the dangerous v6 behavior:** v6's after-loop would have converted STARTED → NOT_PROCESSED in step 6, producing a false result while the student was actually registered. v7 prevents this.

**Case where T2 rolled back (business error) but T3 was never reached:**

1. T1 commits STARTED.
2. T2 rolls back (e.g., email conflict). Error details are in memory only.
3. Connection lost before T3.
4. Importer enters INTERRUPTED.
5. After-loop: finds STARTED child row → leaves it untouched.
6. Reconciliation: STARTED + no audit → NOT_PROCESSED (`was_attempted = NULL`).

The error details are irrecoverable (they existed only in the exception object, never committed). `was_attempted = NULL` is honest: the system cannot prove whether the registration function was invoked. The admin re-uploads this row.

### §11.2. RowOutcome → counter mapping

| RowOutcome | Counter field |
|---|---|
| SUCCEEDED | `imported_count` |
| FAILED | `failed_count` |
| NOT_PROCESSED | `not_processed_count` |
| OUTCOME_UNCERTAIN | `uncertain_count` |
| SKIPPED_PREVIEW_INVALID | `invalid_count` (from preview; not in child table) |

### §11.3. Database-enforced invariants

**`ck_bulk_sessions_preview_counts`:** `total_rows = valid_count + invalid_count` (always).

**`ck_bulk_sessions_import_counts`:**
- Terminal states: `imported + failed + not_processed = valid_count AND uncertain = 0`.
- Non-terminal states: `imported + failed + not_processed + uncertain ≤ valid_count`.

**`uq_row_results_session_index`:** At most one child row per `(session, valid_row_index)`.

### §11.4. Application-enforced invariants

Before writing terminal status (after-loop step 4b), the import loop verifies:

1. `unresolved_count == 0` (no STARTED or OUTCOME_UNCERTAIN child rows).
2. `definitive_count == valid_count` (every index has a definitive child row).

If either check fails, terminal status is NOT written. Session stays PROCESSING.

### §11.5. Reconciliation-enforced invariants

After classifying all rows (step 6), reconciliation verifies:

1. Total child rows = valid_count.
2. No STARTED or OUTCOME_UNCERTAIN child rows remain.

Then recalculates counters from child table and writes terminal status. The CHECK constraint validates on write.

**Response 200** (processing is synchronous — complete before response):

**If all rows resolved (normal completion):**
```json

```

**If unresolved rows remain (interrupted, needs reconciliation):**
```json
{
  "upload_id": "uuid",
  "status": "PROCESSING",
  "total_rows": 95, "valid_count": 90,

  "last_started_valid_index": 50,
  "needs_reconciliation": true,
  "message": "Import interrupted. Trigger reconciliation to resolve uncertain outcomes."

```

**Errors:** 404, 409 (expired/already confirmed).

### §12.3. Get Status / Results — `GET /admin/bulk-uploads/{id}`

**PENDING_CONFIRMATION:** Full preview (email, phone, address visible). Includes `expires_at`.

**EXPIRED:** Stub — counters, `preview_invalid_results`, dates. No `validated_rows`.

**PROCESSING / RECONCILING:** Live counters (from parent table), `last_started_valid_index`, `is_stale` boolean, `needs_reconciliation` (true if `uncertain_count > 0` or stale). No per-row PII.

**Terminal:** Row results from child table (first_name, last_name, roll_number, status, student_id, error info) + `preview_invalid_results`. No email/phone/address. `was_reconciled` from stored column. `was_attempted` per row.

### §12.4. Reconcile — `POST /admin/bulk-uploads/{id}/reconcile`

**Response 200:** Terminal results with recalculated counts and `was_reconciled: true`.

**Errors:** 409 (not eligible — session not stale PROCESSING/RECONCILING), 503 (lock timeout).

### §12.5. Report — `GET /admin/bulk-uploads/{id}/report`

**Response 200:** `text/csv; charset=utf-8`.

Columns: `csv_record_number`, `valid_row_index`, `first_name`, `last_name`, `roll_number`, `status`, `was_attempted`, `error_code`, `error_message`, `corrective_action`, `is_retryable`.

Includes all rows: child-table results (SUCCEEDED/FAILED/NOT_PROCESSED) + preview-invalid rows (SKIPPED_PREVIEW_INVALID from `preview_invalid_results`, with `valid_row_index` = empty, `was_attempted` = empty).

**Formula injection on export:** Every cell checked. First character in `{= + - @ \t \r \n}` OR first non-whitespace in `{= + - @}` → prefix with `'`.

Terminal states only. 409 for others.

### §12.6. List — `GET /admin/bulk-uploads`

Paginated. Filters: `department_id`, `status`. Shows summary counters, no per-row data.

## §13. Privacy, Scrubbing, and Retention

### §13.1. Data classification

| Location | PII content | Scrubbing |
|---|---|---|
| `validated_rows` (parent) | YES: all parsed fields | Scrubbed to `'[]'` atomically with terminal write |
| `preview_invalid_results` (parent) | NONE: record numbers + error codes | Never scrubbed |
| Child table: `first_name`, `last_name`, `roll_number` | LIMITED: names + roll number | Retained until session purge |
| Child table: all other columns | NONE | Retained |
| Audit logs | Roll number, program, term (no email/phone/address) | Append-only, never scrubbed |

### §13.2. Scrubbing atomicity

`validated_rows = '[]'` is set in the same UPDATE that writes terminal status. If the UPDATE commits, PII is gone. If it rolls back, the session is not terminal.

## §14. Audit Behavior

### §14.1. New audit actions

| Action | Value | Trigger |
|---|---|---|
| `BULK_IMPORT_UPLOADED` | `"bulk_import.uploaded"` | CSV parsed, session created |
| `BULK_IMPORT_CONFIRMED` | `"bulk_import.confirmed"` | Session claimed for processing |
| `BULK_IMPORT_COMPLETED` | `"bulk_import.completed"` | Terminal status written by import loop |
| `BULK_IMPORT_INTERRUPTED` | `"bulk_import.interrupted"` | Import loop stopped with unresolved rows; session remains PROCESSING |
| `BULK_IMPORT_RECONCILED` | `"bulk_import.reconciled"` | Reconciliation writes terminal status |

New entity type: `BULK_UPLOAD_SESSION` = `"bulk_upload_session"`.

### §14.2. `bulk_import.interrupted` — transaction and duplication rules (correction 4)

**Transaction boundary:** The interrupted event is committed in the after-loop transaction (§9.4 step 4a). This transaction also inserts NOT_PROCESSED child rows for never-started indexes and updates counters. The session remains PROCESSING — no terminal status is written in this transaction.

**If this transaction fails:** The interrupted event is not recorded. The session stays PROCESSING with stale heartbeat. Reconciliation resolves everything and writes `bulk_import.reconciled` instead. The absence of an interrupted event is acceptable; the reconciled event covers the full story.

**Duplication prevention:** In the synchronous model, the confirm endpoint calls the import loop exactly once. At most one `bulk_import.interrupted` event per session. The import loop is never re-entered for the same session (the confirm endpoint rejects sessions not in PENDING_CONFIRMATION).

**Relationship to `bulk_import.completed`:** These are mutually exclusive for a given session:
- `interrupted` is written when unresolved rows remain (no terminal write).
- `completed` is written when all rows have definitive outcomes (terminal write).
A session that received `interrupted` and was later reconciled will also have `bulk_import.reconciled`.

### §14.3. Per-registration audit extension

When `bulk_origin` is provided, two keys are added to the `STUDENT_REGISTERED` metadata:

```python
metadata["bulk_upload_session_id"] = str(bulk_origin.upload_session_id)
metadata["bulk_upload_row_number"] = bulk_origin.row_index
```

Explicit string-literal keys. No `.update()` from arbitrary dict. `BulkImportOrigin` is frozen with exactly two fields.

**Note:** The audit key is `bulk_upload_row_number` and stores the `valid_row_index` (not the csv_record_number). This is the stable identifier used for reconciliation queries.

### §14.4. Reconciliation audit query

```sql
SELECT entity_id,
       (event_metadata->>'bulk_upload_row_number')::integer AS row_index
FROM audit_logs
WHERE action = 'student.registered'
  AND event_metadata->>'bulk_upload_session_id' = :upload_id_text;
```

Uses `ix_audit_logs_action` index on the `action` column. No GIN index on `event_metadata` is required; the action index narrows the scan sufficiently for ≤100 rows per session.
